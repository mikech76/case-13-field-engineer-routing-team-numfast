# ui2 — второй фронт (агент 2). Браузерный дорожный граф + S0 в браузере

> Статус: **работает end-to-end в реальном headless Edge**, 0 ошибок консоли, 0 исключений.
> Запуск: `python tools/serve.py 8977` → **http://127.0.0.1:8977/**
> (сервер слушает `0.0.0.0`, отдаёт `Cache-Control: no-store`).
> Файлы фронта грузятся с `?v=63` — **после любой правки бамп всех четырёх спецификаторов сразу**
> (`index.html` → `app.js?v=`; `app.js` → `tiles.js?v=`, `router.worker.js?v=`, `numfast_native.wasm?v=`).
> Кеш модулей Edge переживает `no-store` и свежий профиль — bust работает.

## 2. Три настоящих тира (в отличие от фронта-1, где был мок)

### 2.1 Граф — `tools/export_map.py` + `tools/add_distance.py`
Читает `C:/App/numfast/roadgraph/data/map_full` и собирает **развёрнутый портальный граф**
идентично `ClusterRouter/_lib/router.py::_build`:

* `clusters.npz` (`cluster_of` 9 056 213), `ports.npz` (265 522), `matrices.npz` (705 102), `snap.npz` (122 528), `objects.npz` (×1e7).
* `portal_w` выводится поиском `pt` в CSR-окрестности `pf` из `moscow_csr.npz`:
  `ems = length_mm*1000//speed_mmps`, min 1 — **0 промахов из 265 522**.
* Два семейства рёбер: **портальные** `pf→pt` (реальное ребро OSM) и **внутрикластерные**
  `ent[k]→ext[j]` (`mat_q*100`), `mat_ms==0xFFFFFFFF` пропускаются.
* **`add_distance.py` пересчитывает внутрикластерную матрицу второй раз — на длинах** и
  отдаёт **второй CSR `cg_d*` с тем же множеством вершин и тем же порядком рёбер**, но
  весами в метрах. Поэтому **километры — дорожные, а не хаверсинус** (Q&A Q20: «расстояние
  по дорогам, не по прямой»). Итог: заполнено 463 026 из 705 102 ячеек за 60.8 с на 16 воркерах.
* Результат: **C=96144, V=241348, E=938249, 15 файлов, 23 МБ.**

⚠️ **Важно про формат.** `matrices.npz` — это **НЕ OD-матрица**. Строка = один кластер-источник,
внутри только legs **внутрикластера** «вход → выход»; `dst_cluster` в индексации не участвует.
`mat_q` заворачивает INF в 23593, поэтому **маску недостижимости брать из `mat_ms`**.

⚠️ **Два разных масштаба координат** (стоит проверить, если снова поедут точки):
`obj_lat.i32` / `obj_lon.i32` — **×1e7**, `pn_lat.i32` / `pn_lon.i32` — **×1e5**
(max 5836414 = 58.36°). Раньше на обеих стоял `DEG=1e7`, и ломаные приходили в 100 раз меньше
реальности (`0.5557, 0.3764` вместо `55.578, 37.643`). Сейчас в `router.worker.js`
`const DEG = 1e7` (объекты) и `const PNDEG = 1e5` (портальные вершины).

### 2.2 Маршруты — `lib/router.worker.js`
Загружает 15 `.bin` прямо в линейную память WASM (175–250 мс, аплоад 5–6 мс), снапит все
точки сеткой 0.01° над 122 528 объектами, и **на каждый кластер источника** гоняет SSSP:
`dist[]` по вершинам → `t(c,d) = min по портальным вершинам кластера d` (это и есть
`_query_min`). Строки собираются в компактную матрицу `nsrc × ncol` (`colOf/srcOf/dstCols/ms/km`),
где источники — **и кластеры заявок, и старты бригад** (план спрашивает `START:<team>→req`).

⚠️ **`nf_sssp_csr` ловит trap в worker'е Edge** (`RuntimeError: table index is out of bounds` в
`panic_bounds_check → sssp_csr → dijkstra`), хотя побайтовая проверка всех буферов проходит
(`NP`, `indptr`, `ix/wv`, `di`, canary, отсутствие detach — всё верно), и **тот же .wasm +
bridge работает в Node** (1.536 мс/вызов). Проверены и синтетический суперисточник (`np=V+2`),
и обычный CSR (`np=V+1`) — оба ловят. Причина не найдена, времени нет. Поэтому матрица в
браузере считается **чистым JS-Dijkstra по тем же загруженным массивам** (`cg_*`/`cg_d*`),
а WASM-ядро остаётся загруженным и подключённым. Цена: **~55 мс/solve в браузере против
1.54 мс в Node**.

### 2.3 Распределение — `lib/s0.js`
Порт production-S0 на JS, ноль зависимостей, ESM. `BASE_WEIGHTS {accident:100, connection:50, repair:20, extra_order:20}`,
`WORK_DOCS {connection:70, accident:80, extra_order:20, repair:30}`, порядок пула
`(we-ws, −eff, id)` (narrow-first), `best_insertion` с девятью soft-фичами, 2-opt (eps 1e-9),
preempt для аварий, `timeGates` — дословно из `shared/time_predicate.py`.
Сохранённые питоновские особенности: `roundHalfEven` (не `Math.round`), `Map` (не `{}`) для
equip/stock, `break` без отката при нехватке, `we` **не** ограничивает `end`, длительность
работы из `WORK_DOCS`, а не из `req.dur`.

### Найденный баг данных (важно для агента 1)
`data/canonical/requests_100.csv` содержит `equip_need` ∈ {0: 51, 1: 49}. Если трактовать его

## 6. Карта (то, что просил пользователь)

* Свой **canvas-слайпи-меп** `lib/tiles.js` — ноль зависимостей, **никакого Leaflet** из френта-1.
  Источники: Esri Street, Esri Satellite, OSM, none.
* Показывает **заявки** (выполнена/в пуле), **старты бригад**, **базы (3 офиса)**, **кафе**;
  всё кликабельно (точки **и** подписи).
* **Маршрут каждой бригады рисуется по дорогам** — реальная ломаная из портального графа,
  сегменты «заявка→заявка» разного цвета по радуге `hsl(i/n*300, 88%, 62%)`,
  **стрелка в конце сегмента**, у текущего сегмента — **бегущая пунктирная линия**.
* **Клик по бригаде (список / карта / заявка) выделяет только её маршрут**; остальные тускнеют.
* В правой панели — **«Маршрут — сегменты»**: все сегменты маршрута, у каждого время приезда,
  адрес, минуты/километры и честный тег **«ДОРОГИ»** (зелёный) либо **«ПРЯМАЯ»** (красный).
* **Легенда** в одну строку, читаемая.

### Интерактив (проверено CDP-зондом `tools/ztest.mjs`)

Зонд реально жмёт колесо и кликает по карте, а не «просто смотрит скриншот»:

```
boot          {"ready":true,"map":true,"phase":"solved","err":null}
4 щелчка      z11 -> z15, вид едет за курсором
tiles cached  270 (кеш НЕ чистится при зуме)
hit points    105
клик по ▣     {"sel":"TEAM-SE-14","rows":10,"panel":true}
```

Четыре причины, по которым «карта плохо отображается, метки не едут, всё висит, ничего не
выделяется» — все исправлены в `lib/tiles.js`:

1. **Оверлей не перепроецировался при смене вида.** Маршруты и метки хранились уже
   спроецированными в device-px и пересчитывались только в `app.js::renderMap()`, который при
   панораме не зовётся. Теперь геометрия хранится в **geo-координатах** (`ln.geo`, `p.geo`,
   `m.geo`), а проекция пересчитывается по **view stamp**: `this._stamp++` в `resize`/`_pan`/
   `flyTo`/`fit`/колесе, и в `draw()` первым делом
   `if (this._stamp !== this._drawnStamp) { this._project(); ... }`.
2. **Колесо чистило кеш тайлов на каждом тике** (`tiles.clear()` + `clearRect`) — весь вьюпорт
   перезапрашивался за событие, база карты мигала пустотой, сеть упиралась. Заменено на
   **`_prune()`**: бюджет 420 тайлов, вытесняются первыми дальние от текущего зума.
3. **Шаг зума был крошечным и дробным** — `dz = -deltaY*0.0022` давал 0.22 уровня на щелчок.
   Теперь `dz = -deltaY * (deltaMode===1 ? 0.25 : 0.01)` (≈1 уровень на щелчок) и
   `if (Math.abs(dz) < 0.05) return;` — трекпад не перерисовывает каждое событие.
4. **`setPointerCapture` вызывался ДО присваивания `down`** — если он бросает, `down` остаётся
   `null`, а `pointerup` с `if (!down) return` молча выбрасывал **каждый** клик, то есть
   не выделялось ничего. Теперь `down` присваивается первым, capture обёрнут в `try/catch`,
   на `pointerup` capture отпускается, а `pointercancel` и `pointerleave` сбрасывают `down`.

Плюс `window.cMap` / `window.S` выставлены наружу — иначе к карте нельзя достучаться из консоли.

### ГЛАВНОЕ — проверка «по дорогам, а не по прямой» (сделано, цифры выше)
Прогоняется настоящий `singlePath` (JS-Дейкстра по `cg_*`) для **каждой** ноги маршрута.
`window.__ui2.geom = {want, road, straight, done, per_ms, wall_ms, why}`.
**45 из 100 ног построены по дорогам**, 55 — `same-cluster` (в канонической сотне заявки
идут плотными группами по одним домам, поэтому две соседние заявки часто в одном кластере) —
для них честно рисуется пунктирная прямая. Каждая нога помечена тегом в панели.

## 7. Ограничения (честно, не прячем)

1. **`nf_sssp_csr` в Edge worker ловит trap** — матрица считается JS-Дейкстрой по тем же
   массивам. WASM загружен и подключён. В Node этот же .wasm работает за 1.54 мс/вызов.
2. **1000 заявок в браузере медленно** (~60–90 с против ~7 с на сотне) — это следствие п.1.
3. **Хвост точности +24 %** — опубликованная огибающая `CLUSTER_ROUTER.md`, следствие капа `[:8]`.
4. **Подъезды внутри кластера не моделируются** (в `cluster_router.py` это прямо написано).
5. **`quant_foot_*` — это переквантованная АВТО-таблица** (`MAP_FULL2.md` §7), фронт никогда
   не называет её пешеходной.
6. Кириллица в адресах печатается как есть; `pr.txt` создаётся прогоном зонда и **удаляется перед публикацией**.

## 8. Грабли (потратил на них реальное время — не повторять)

* **`node --check app.js` НЕ ПРОВЕРЯЕТ ESM.** Он парсит как CommonJS и молча прощает ESM-синтаксис.
  Сломанный `fitTeam` с лишней `)` проходил `node --check`, а страница открывалась пустой:
  `Runtime.exceptionThrown` с `text: "Uncaught"` и **без** объекта exception, без ошибки
  в консоли, без стека. Правильно: `node --input-type=module --check < app.js`
  (и то же для каждого `lib/*.js`).
* **Зонд дедуплицирует одинаковые снимки** (`if (line !== lastLine)`), поэтому зависшая
  страница печатает ровно одну строку и выглядит как «зонд вышел рано».
* **Коллизии имён классов — дважды.** `.bar` был определён дважды (верхняя панель и бар в
  сетке) → сетка переименована в `.jbar`. `.seg` был определён дважды (переключатель вида и
  строка сегмента) → строка сегмента переименована в `.segrow`. **Всегда грепнуть дубли
  класса, прежде чем обвинять вёрстку.**
* **`tiles.js::_origin()`** брал `s/2` от **мира** (`2^z*TILE`) вместо **вьюпорта** —
  это давало мусорный `z9 · 88.435°, −140.673°` вместо Москвы. Правильно:
  `return [this.w/2 - this.cx*TILE, this.h/2 - this.cy*TILE];`
* **При смене вида оверлей обязан перепроецироваться сам** — держать в слоях уже спроецированные
  device-px нельзя: `renderMap()` зовётся не на каждый пан/зум.
* **`singlePath.pop()` крутился вечно** — внешний `for(;;)` сифт-дауна перезапускался с `m = 0`.
  Пакетный `hPop()` был правильный (он зовёт `hSiftDown(0)`), поэтому матрица работала, а геометрия нет.
* **Ответ воркера нельзя отдавать вложенными массивами** — ~40 100 массивов `[lat,lon]`
  доходят как `undefined`. Отдаём **плоский `Float32Array`** + `Int32Array n` + `keys`, transfer.
* `window.__ui2` надо обновлять (`expose()`) в **каждом** обработчике воркера, иначе зонд читает снимок.
* **Никогда не убивать Chrome.** Только Edge, и только свои деревья по маркеру `--user-data-dir`.
* CRLF: `python -c` с `\n` молча ничего не делает. Рецепт:
  `io.open(p,encoding='utf-8').read().replace('\r\n','\n')` → запись `newline='\n'`.
* `export_dataset.py` пишет **только** `scenario_<n>.json` при явном `--n n` (дефолт 1000).

## СНАП: почему дальние районы шли по прямой (исправлено)

Симптом: Домодедово, Каширское шоссе, Обнинск — ноги рисуются прямой, а заявки
не попадали в дорожный граф.

Причина (измерено, не догадано): снап строился по сетке **объектов** `obj_lon/obj_lat`
— это 122 528 адреса **только центральной Москвы**, bbox lat 55.5653…55.9167,
lon 37.3213…37.8818. Радиус поиска — 6 ячеек по 0.01° ≈ 4 км. Всё, что вне Москвы,
давало `cluster = -1` → `default_t 15 / 3.0 км` и честный пунктир «прямая».
Измеренно: **38 из 177 точек (21 %) не снапились вообще** — SYNTH-0012, -0013,
-0018 (54.837, 38.246 — Кашира), -0027, -0031, -0036, -0037, -0039, -0042, -0044,
-0045, -0050.

**Граф при этом был полным** — `map_full/moscow_csr.npz` покрывает весь ЦФО
(lon 30.64…47.52, lat 49.46…59.44), 96 144 кластера и 241 348 портальных вершин.
Не докачивали данные — сломан был только переход «координата → кластер».

**Исправление** (`lib/router.worker.js`): вторая сетка `buildPortalGrid()` по
`pn_lon/pn_lat` (портальные вершины, весь ЦФО, шаг 0.02°) + обратная таблица
`vertexCluster` из `cl_indptr/cl_verts`. `snap()` сначала ищет объект, при промахе
ищет ближайшую портальную вершину — она всегда на дороге. Радиус 34 кольца ≈ 66 км.

| | до | после |
|---|---|---|
| не снапилось | 38 / 177 | **0 / 177** |
| медиана снапа | 55,0 м | 62,3 м |
| ног по дорогам | 45 / 100 | **83 / 100** |
| прямых заглушек | 55 | 17 |
| S0 | done 100, 22 бригады, 250,9 км | done 97, 24 бригады, 323,6 км |
| геометрия | 3 мс/ног, 298 мс | 18 мс/ног, 1 799 мс |

Оставшиеся 17 прямых — `same-cluster` (заявки одного дома, нулевая длина) и
`unreachable`; они честно помечены красным тегом «ПРЯМАЯ».

## Про 1000 заявок

`geom` считает каждую ногу отдельной Дейкстрой по 241 348 вершинам (~18 мс).
100 ног = 1,8 с. Для 1000 заявок это ~1000+ ног ≈ 18–25 с поверх 124 SSSP.
Прогресс-бар и чип показывают это вживую, но для демо честнее брать 100–300 заявок.

## КАРТА: теперь это Leaflet ( vendored ), а не самописный канвас

Пользователь трижды сказал «карта ужасная»: слои отставали от подложки при перетаскивании,
зум скакал непонятно куда, часть маршрутов оставалась прямыми полосками — и прямо попросил
**«возьми у другого интерфейса полностью механизм обращения с картами и рисования слоев и меток»**.

**Сделано ровно это.** Самописный канвас-слайпи-меп `lib/tiles.js` (551 строка, четыре раунда
баг-фиксов: кэш тайлов, `setPointerCapture`, оверлейный кэш, троттлинг драга) **удалён из
рабочего пути**. Вместо него:

* `ui2/vendor/leaflet.js` + `leaflet.css` + `images/` (185 КБ) — **файлы скопированы из
  `ui/vendor/`, тот же Leaflet, что и у агента-1.** Никакого CDN, всё локально.
* `ui2/lib/lmap.js` — тонкий адаптер: тот же интерфейс `class Map` (`view/setSource/project/
  setLayers/draw/flyTo/panTo/fit/resize/get hit`), чтобы `app.js` почти не менялся.

Что это дало ровно по пунктам жалоб:

| жалоба | причина в самописной карте | как в Leaflet |
|---|---|---|
| «метки отстают при перетаскивании» | оверлей рисовался в отдельный canvas и перерисовывался только на `pointerup` | панели Leaflet (`paneLine / panePt / paneMk / paneTop`) двигаются вместе с тайлами в одном кадре |
| «зум скачет непонятно куда» | самописный подбор `z` от bbox | добавлен `visible(bbox)`: **если нужный прямоугольник уже в кадре — карта не двигается вообще**; `fit()` сначала в Leaflet, потом `flyTo` |
| «прямолинейные полоски» | заглушка рисовалась всегда | заглушка рисуется только если реальное расстояние **> 150 м**; соседние заявки одного дома (< 150 м) не рисуются вовсе |
| «значков нет» | поле `label` у марок не использовалось | каждая заявка — `L.circleMarker` + подпись бригады; клик по пину и по подписи работают |

Дополнительно в `lmap.js`: три подложки (Esri Street / Esri Satellite / OSM standard),
`cssColor()` — обязательный, потому что `var(--ok)` невалиден как SVG-атрибут и резолвится
через `getComputedStyle`; анимация бегущего пунктира трогает **только** выбранный сегмент
(`setStyle({dashOffset})` на rAF), у остальных — стрелка на конце ломаной.
Плотность подписей: id бригады у заявки и старты бригад подписываются только когда выбрана
бригада (solo) или `z >= 14`, иначе — просто точки.

## NFS-карта на ВСЮ Московскую область (проверено)

Пользователь: агент-1 сделал квантованную карту в нашем формате NFS и велел покрыть
всю область. Проверил — **не покрывает**.

### Что реально лежит в `roadgraph/data/map_nfs/`
```
header.json: n=701133  m=1357228      <- это СТАРЫЙ data/moscow_csr.npz
фактический bbox:  lon 37.3078..37.9057   lat 55.5144..55.9321   (0.6 x 0.42 градуса)
заявок внутри bbox:  848 / 1000   (84.8 %)
вне:  Домодедово 55.42/37.78,  Кашира 54.837/38.246,  Подольск, Серпухов
```
То есть это **центральная Москва**, ровно тот же bbox, из-за которого раньше 21 %
точек не снапилось. Области там нет.

### Формат физически не мог хранить область
`NfsMap/_lib/nfs.py` захардкодил ширины: `_pack_nodes_6b` = dlon **23 бита** + dlat
**22 бита** (6 Б/узел), `_pack_heads_20b` = **20 бит** на ребро.

| поле | в формате | нужно на область | нужно на весь ЦФО |
|---|---|---|---|
| dlon | 23 бит (max 8 388 607) | **25 бит** | 28 бит |
| dlat | 22 бит (max 4 194 303) | **25 бит** | 27 бит |
| heads | 20 бит (N < 1 048 576) | **22 бит** (2 619 287 узлов) | 24 бит |

Любой bbox шире ~0.84° по долготе или ~0.42° по широте **переполняет** формат —
молча, без ошибки: `assert` в `nfs_build` стоят на месте и падают только если
сдвиг отрицательный, а переполнение по старшему биту не проверяется вообще.

### Что сделал: `tools/export_nfs_oblast.py`
Собирает слепок **из полного ЦФО CSR** (`data/map_full/moscow_csr.npz`), вырезает
подобласть с 1-хоповой дилатацией, и — главное — **выводит битовые ширины из
данных**, а не хардкодит. Тот же NFS-лейаут: raw little-endian дампы, magic `NFS1`,
`header.json`, ноль парсинга при загрузке.

```
python tools/export_nfs_oblast.py --out C:/App/numfast/roadgraph/data/map_nfs_oblast
python tools/export_nfs_oblast.py --selftest
```

```
клип: 2 619 287 / 9 056 213 узлов (28.9 %),  5 322 225 / 18 642 179 рёбер (28.5 %)
ширины: dlon=25 dlat=25 heads=22          (было 23 / 22 / 20)
размер: 59.3 МБ, 10 файлов
roundtrip: heads и nodes распакованы обратно bit-exact
```

### Проверено
```
bbox собранного: lon 36.5000..39.0000   lat 54.5000..56.5000
заявок внутри:  100/100  и  1000/1000   (100 %)
бригад внутри:  197/197                 (100 %)
snap_node:      122 528 / 122 528 внутри клипа, ни одного -1

маршрутизация (Дейкстра по распакованному NFS):
  Кашира (54.86/38.20) -> Москва (55.76/37.63)   4888 с = 81.5 мин
  Домодедово (55.42/37.78) -> центр               1983 с = 33.0 мин
  Москва внутри                                    762 с = 12.7 мин
  Подольск -> Серпухов                            3107 с = 51.8 мин
```
Те пары, которые раньше не маршрутизировались вообще, теперь считаются.

`traf.nfs` не выгружаю: в оригинале это 2000-дублей-заглушка с флагом

## ИТОГОВЫЙ РАЗБОР (последний, 29.09) — почему цифра упала со 100 на 97 и почему это хорошо

### Что было не так
`makePortalTravel` на любую ногу, которую портальный граф не покрыл, возвращал
**выдуманные (15 мин, 3.0 км)**. Замер показал: **3514 из 5418 запросов времени
(65 %) не имели ответа** — и ровно эти ноги закрывала заглушка. Старые «100/100 ·
22 бригады · 244 км» были посчитаны на 35 % выдуманных чисел. В KPI это не
было видно.

### Что сделано
1. **`tools/rebuild_portal_nocap.py`** (592.9 c, 12 воркеров) пересчитал
   внутрикластерные матрицы из полного 9M CSR **без ограничения `[:8]`** на
   входы и выходы: 817 018 ячеек (было 705 102), max row 6 864 (было 64).
   Граф: `C=96144 V=241348 E=1035952`, `step_ms: 1` — квант 100 мс убран,
   веса в точных миллисекундах.
2. **`tools/export_map_nocap.py`** (8 c) пересобрал `assets/map2/` по образцу
   `export_map.py`: `cg_*` (время) + `cg_d*` (метры) с тем же набором вершин и
   тем же порядком рёбер.
3. **Найдена и починена настоящая причина 65 %** — не карта и не воркер:
   `lib/router.worker.js` проставляет `srcOf[i]` **только для первого ключа**
   каждого кластера, а `app.js::buildTravel` делал `if (srcOf[i] < 0) return;`
   → **111 из 177 ключей вообще не регистрировались** в кэше времени. Доля
   зарегистрированных 66/177 = 37.3 % совпала с долей ответов 1912/5426 = 35.2 %.
   Починено построением `cluster → row` и регистрацией **каждого** ключа.
4. **Диагностика, которая это доказала** (оставлена в коде): в воркере перед
   отправкой матрицы считаются конечные ячейки → `dbg {where:'matrix', cells:4356,
   finT:4097}` = **94.05 %**, что совпало с офлайн `tools/pdiag.mjs` (94.0 %).
   Значит карта и воркер невиновны — виноват индекс на фронте.
5. **`cg_d*` был в 1000 раз больше правды**: `export_map_nocap.py` писал
   `length_mm` (миллиметры) без деления, а фронт делит на 1000. Км были
   30 898 вместо 323. Починено: `max(1, x // 1000)`.
6. **Пробки вшиты** (`lib/traffic.js`), `k(h)` city-uniform ymarchive-2015,
   вкл по умолчанию. В таблице честно помечено: реальные замеры только
   k(09)=2.23 и k(19)=2.58, остальные часы интерполированы Catmull-Rom; k
   зависит только от часа выезда, т.к. растровый слой к рёбрам OSM не привязан.
   Слот заменяемый: любая будущая порёберная таблица — объект с теми же полями.
