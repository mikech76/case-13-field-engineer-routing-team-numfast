# NumFast — диспетчерская выездных инженеров

**ЛЦТ 2026 · задача 3 «Интеллектуальный сервис планирования рабочих маршрутов для инженеров с учётом временных окон и сложности работ» · Билайн Бизнес**

---

## Главное в одной строке

Мы **не брали готовый планировщик и не поднимали бэкенд**. Мы написали собственный
счётчик маршрутов на собственной библиотеке **numfast**, поквантовали дорожный граф
Центрального Федерального округа и **считаем маршруты и распределение заявок прямо
в браузере** — без Python-сервера, без OSRM, без внешних API.

---

## Почему это главное отличие

| | Типовое решение | Наше |
|---|---|---|
| Матрица расстояний | внешний OSRM / Valhalla, **нужен бэкенд** | собственный roadgraph, квантованный граф ЦФО |
| Оптимизатор | Google OR-Tools, лимит поиска 10 с | свой S0 (narrow-first → insertion → 2-opt → preempt) |
| Где считается | сервер | **вкладка браузера** |
| Время на 197 заявок | 3 × 5…120 с | **0.10 с** (в Node, на том же .wasm) |
| Время на 10 000 заявок | часы | 0.6 с (E2E, кэш) |
| Точность расстояний | OSRM — точно | кластерно-квантованная: медиана +0.6 %, хвост +7 % |

Официальный Q&A прямо говорит, что OR-Tools не обязателен (вопрос 52) и что
расстояние должно считаться **по дорогам, а не по прямым** (вопрос 20). Мы сделали
дороги и не взяли чужой оптимизатор.

## Как это работает — три ступени, все в браузере

### 1. Дорожный граф: квантованный портальный граф ЦФО

Из полного CSR Центрального Федерального округа (**9 056 213 узлов, 18 642 179
рёбер**, bbox lon 30.64…47.52 / lat 49.46…59.44) кластеризацией L1 (Voronoі,
96 144 кластера, 265 522 порта) и **пересчётом внутрикластерных матриц от всех
входов и выходов без ограничения `[:8]`** собирается **развёрнутый портальный
граф**:

```
C = 96 144 кластеров
V = 241 348 портальных вершин
E = 1 035 952 ребра
шаг кванта = 1 мс   (было 100 мс — квантование снято)
817 018 внутрикластерных ячеек, 770 430 пригодных
```

Отдельно строится **второй CSR с теми же вершинами и тем же порядком рёбер, но
весами в метрах** — поэтому километры в интерфейсе настоящие дорожные, а не
хаверсисные (вопрос 20).

### 2. Маршруты: SSSP по портальному графу

Один поиск кратчайшего пути на **каждый кластер**, за которым стоит заявка или
старт бригады, даёт времена сразу до всех остальных кластеров:
`t(c, d) = min по портальным вершинам кластера d`. Два прогона на источник —
время и метры. 132 Дейкстры на 100 заявок = **8.2 с** в браузере.

### 3. Распределение: S0 на JavaScript

Порт продакшн-S0 (`lib/s0.js`), **бит-в-бит по документации оригинала**:

* порядок пула — narrow-first `(we − ws, −eff, id)`;
* вставка в маршрут по минимизации `(Δкм, −soft, pos)` при **строгом** `<`;
* 9 soft-признаков с нормировкой 120 мин / 30 км / 3 км;
* 2-opt с eps 1e-9;
* вытеснение (preempt) для аварий;
* `time_gates` — единый источник истины по времени: ворота в порядке
  **прибытие → окно → смена**, и `we` никогда не ограничивает `end`.

**34 мс на 100 заявок**, целиком в браузере.

### Честная воронка отказов

Интерфейс показывает **почему** заявка не выполнена, а не молчит:

```
портальный граф не перекинул мост   3
не успеть к окну                    1
времён: портал 36 960 · точная матрица 0 · без ответа 422
```

Три «не перекинул мост» — хвост под Каширу и Домодедово, где кластер не
сцепляется в цепочку. Мы **намеренно не рисуем там прямую линию**: такая полоса
была бы враньём, поэтому нога просто помечена как не построенная. Вопрос 49
прямо требует отмечать, что не влезло.

## Про две разные цифры, которые нельзя ставить рядом

Это важно, чтобы не выглядело ошибкой:

| Срез | done | Что это |
|---|---|---|
| **Здесь, в браузере** | **97 / 100** | конкурсные CSV, экипировка снята как ограничение, неквантованный портальный граф, пробки вкл |
| Наш второй фронт на Python | 82 / 100 | тот же срез, но его фикстуры используют сырые русские `rtype`/`skills`, из-за чего `BASE_WEIGHTS` никогда не срабатывает и каждая заявка получает приоритет 0 |
| Продакшн `run.py` | 89 / 787 | другой путь кода и другой срез |

**98/100, 89/787 и 97/100 — это разные срезы. Ставить их рядом нельзя.**

## Честные ограничения

1. **Кластерная, а не поузловая точность.** Внутрикластерные подъезды (от дороги
   до подъезда) не моделируются — это свойство формата, а не нехватка данных.
   Проверено против точного Дейкстры на полном CSR: медиана +0.6 %, хвост +7 %.
2. **Пробки — равномерные по городу.** `k(h)` — реальные значения ymarchive 2015
   (k(09)=2.23, k(19)=2.58), остальные часы интерполированы и **это не измерения**.
   Зависит только от часа выезда, потому что растровый слой пробок к рёбрам OSM
   ещё не привязан. Слот сделан заменяемым: настоящая таблица подставляется
   без переделки кода.
3. **3 ноги в хвосте области не строятся** — см. воронку выше.
4. **WASM-ядро `nf_sssp_csr` ловит trap в воркере Edge**, хотя тот же `.wasm` даёт
   1.536 мс на запрос в Node. Поэтому в браузере матрица считается JS-Дейкстрой по
   тем же загруженным массивам (58 мс/решение вместо 1.5 мс), а WASM-модуль
   остаётся загруженным и подключённым. Причина внутри Rust-стека не локализована.

Все ограничения перечислены и в `docs/TECH_REPORT.md`.
